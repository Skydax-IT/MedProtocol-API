# MedProtocol API — Codex Master Prompt & Technical Blueprint

**Project name:** MedProtocol API  
**Product type:** API-first clinical triage protocol engine  
**Brief version:** 0.2 — FastAPI/Python MVP Demo  
**Status:** Prototype / demo only — **not clinically validated, not for real patient care**  
**Primary language:** French for user-facing outputs, English-ready internal naming  
**Target clients:** NGOs, ministries of health, digital health integrators, donor-funded health programmes, SMS/USSD providers, field health applications, DHIS2/OpenMRS/CommCare/OpenSRP-like ecosystems.  
**Primary developer profile:** Solo founder / solo developer using Codex.  
**Architecture objective:** Professional enough for future B2B/B2G due diligence, simple enough to build and maintain alone.

---

## 0. Executive framing

MedProtocol API is **not** a medical AI, **not** a diagnosis engine, **not** a virtual doctor, and **not** a consumer health app.

MedProtocol API is a **headless, deterministic, protocol-based triage engine** designed to be integrated into existing field health systems. Its role is to help partner systems answer:

> “What should the field worker do now, with the observed signs, available resources, country context, and user role?”

The MVP must demonstrate architecture and integration patterns only. It must use **demo clinical rules** that are explicitly marked as non-validated and not suitable for real clinical use.

The long-term vision is to turn validated protocols into:

- deterministic rules;
- versioned protocol packs;
- auditable triage decisions;
- offline-capable bundles;
- integration-ready API responses;
- SMS/USSD/app-friendly outputs;
- safe role-based guidance.

## 2. Why this stack

The stack must balance professionalism and solo-founder speed.

### Recommended MVP stack

| Layer | Choice | Reason |
|---|---|---|
| Backend framework | FastAPI | Fast to build, typed, excellent OpenAPI generation, production-ready API framework. |
| Language | Python 3.14+ / fallback 3.13 | Python is readable and strong for rule engines, data validation, health informatics prototypes, and solo development. |
| Validation | Pydantic v2 | Strong typed schemas, validation, JSON Schema/OpenAPI compatibility. |
| Database | PostgreSQL 18 | Stable open-source relational database suitable for audit, tenants, protocol versions, and future analytics. |
| ORM | SQLAlchemy 2.0 | Mature Python ORM with enterprise-grade patterns. Avoid SQLAlchemy 2.1 beta for MVP stability. |
| Migrations | Alembic | Standard migration tool for SQLAlchemy. |
| Testing | Pytest | Python testing standard, simple and powerful. |
| Package manager | uv | Fast modern Python dependency management. |
| Lint/format | Ruff | Fast, simple, low-maintenance linting and formatting. |
| Type checking | Pyright or mypy | Stronger maintainability and safety. |
| Local infra | Docker Compose | Easy local PostgreSQL and reproducible developer setup. |
| API docs | FastAPI OpenAPI / Swagger / ReDoc | Integration-first documentation for clients. |

### Why not NestJS for this MVP

NestJS remains a strong enterprise backend framework, but for a solo founder it adds more boilerplate, more concepts, and a heavier folder structure. MedProtocol API’s hardest problem is not HTTP routing; it is:

- explicit clinical rule modelling;
- auditability;
- versioning;
- safety constraints;
- integration documentation;
- determinism;
- future offline execution.

FastAPI gives a faster path to a serious MVP while keeping professional standards.

## 3. Product boundaries

### MedProtocol API does

- Receive structured clinical/contextual inputs.
- Ask the next most important triage question.
- Detect demo danger signs.
- Classify demo urgency level.
- Suggest safe demo action categories such as “urgent referral recommended”.
- Adapt output based on user role.
- Return missing critical data.
- Return SMS/USSD-friendly summaries.
- Return protocol/rule metadata.
- Create auditable decision records.
- Export future offline bundles.

### MedProtocol API does not do

- Diagnose patients.
- Replace a clinician.
- Provide autonomous medical advice.
- Prescribe medication.
- Recommend dosages.
- Perform free-text medical reasoning.
- Invent protocols.
- Override national protocols.
- Store unnecessary personally identifiable information.
- Function as a complete DHIS2/CommCare/OpenMRS replacement.

## 7. Domain concepts

### 7.1 Tenant

A tenant represents a client organization:

- NGO;
- ministry;
- digital health integrator;
- donor-funded programme;
- demo client.

Required fields:

```text
tenant_id
name
status
allowed_countries
allowed_modules
created_at
updated_at
```

### 7.2 API key

API keys authenticate tenants.

Rules:

- never store plaintext keys;
- store only hashed keys;
- show full key only once at creation;
- support key prefix for lookup;
- support revocation;
- support expiry;
- log key ID, never key value.

### 7.3 Protocol

A protocol is a versioned source of rules.

```json
{
  "protocol_id": "demo_child_danger_signs",
  "title": "Demo child danger signs protocol",
  "source_label": "Demo only - not a medical source",
  "country": "generic",
  "module": "child_triage",
  "version": "DEMO_DRAFT_NOT_VALIDATED",
  "status": "draft",
  "validation_status": "demo_only",
  "clinical_use_status": "not_for_real_patient_care",
  "effective_from": "2026-06-28",
  "deprecated_at": null
}
```

### 7.4 Rule

A rule is a deterministic condition/action unit.

```yaml
rule_id: demo_child_danger_001
protocol_id: demo_child_danger_signs
protocol_version: DEMO_DRAFT_NOT_VALIDATED
validation_status: demo_only
clinical_use_status: not_for_real_patient_care
priority: 100
patient_group: child_0_59_months
module: child_triage
condition:
  any:
    - path: clinical_inputs.danger_signs.convulsions
      operator: equals
      value: true
    - path: clinical_inputs.danger_signs.lethargy_or_unconscious
      operator: equals
      value: true
    - path: clinical_inputs.danger_signs.unable_to_drink_or_breastfeed
      operator: equals
      value: true
result:
  urgency_level: urgent_referral
  referral_required: true
  action_code: urgent_referral
  reason_code: demo_danger_signs_detected
  detected_danger_signs:
    - convulsions
    - lethargy_or_unconscious
    - unable_to_drink_or_breastfeed
safety:
  allow_medication: false
  allow_dosage: false
```

### 7.5 Country pack

A country pack configures localization and enabled modules.

```yaml
country_code: CF
country_name: Central African Republic
status: demo
languages:
  - fr
enabled_modules:
  - general_triage
  - child_triage
  - pregnancy_triage
clinical_use_status: not_for_real_patient_care
referral_wording:
  fr: "Référer vers la structure de santé appropriée selon le circuit local."
notes:
  - "Demo pack only. Requires national validation before any real use."
```

### 7.6 Scope of practice

The scope layer adapts outputs according to user role.

Example:

```yaml
role: community_health_worker
display_name: Agent de santé communautaire
allowed_action_categories:
  - identify_danger_signs
  - recommend_referral
  - ask_missing_questions
  - provide_simple_explanation
forbidden_action_categories:
  - diagnosis_confirmation
  - prescription
  - dosage
  - invasive_procedure
  - advanced_clinical_assessment
output_constraints:
  max_sms_chars: 160
  avoid_terms:
    - diagnostic certain
    - traitement définitif
```

## 10. Pydantic schema guidance

Use Pydantic v2 models for every request and response.

Example domain-facing schema:

```python
from enum import StrEnum
from pydantic import BaseModel, Field, ConfigDict

class PregnancyStatus(StrEnum):
    pregnant = "pregnant"
    not_pregnant = "not_pregnant"
    not_applicable = "not_applicable"
    unknown = "unknown"

class Sex(StrEnum):
    female = "female"
    male = "male"
    unknown = "unknown"

class PatientContext(BaseModel):
    model_config = ConfigDict(extra="forbid")

    patient_ref: str | None = Field(default=None, description="Optional external pseudonymous reference. Avoid direct identifiers.")
    age_months: int | None = Field(default=None, ge=0, le=1500)
    sex: Sex = Sex.unknown
    pregnancy_status: PregnancyStatus = PregnancyStatus.unknown
    weight_kg: float | None = Field(default=None, ge=0, le=300)
```

Validation principles:

- Use `extra="forbid"` to reduce accidental data ingestion.
- Restrict enum values.
- Validate units explicitly.
- Avoid names, phone numbers, street addresses, and national IDs.
- Allow `patient_ref` only as a pseudonymous external reference.
- Reject obvious invalid vitals.

## 12. Rule engine design

The decision engine must be deterministic.

### Evaluation steps

```text
1. Validate input schema.
2. Normalize input.
3. Resolve tenant capabilities.
4. Resolve country pack.
5. Resolve user role scope.
6. Resolve applicable module(s).
7. Load applicable rules by protocol version.
8. Sort rules by priority descending, then rule_id ascending.
9. Evaluate danger-sign rules first.
10. Collect triggered rules.
11. Determine urgency level.
12. Detect missing critical data.
13. Apply scope-of-practice constraints.
14. Compose output.
15. Persist audit.
16. Return response.
```

### Supported operators for MVP

```text
equals
not_equals
exists
not_exists
in
not_in
greater_than
greater_or_equal
less_than
less_or_equal
any
all
```

### Rule condition example

```yaml
condition:
  all:
    - path: patient_context.age_months
      operator: greater_or_equal
      value: 0
    - path: patient_context.age_months
      operator: less_or_equal
      value: 59
    - any:
        - path: clinical_inputs.danger_signs.convulsions
          operator: equals
          value: true
        - path: clinical_inputs.danger_signs.lethargy_or_unconscious
          operator: equals
          value: true
```

### Determinism requirements

- Never depend on random values during evaluation.
- Never call external APIs during rule evaluation.
- Never call an LLM during rule evaluation.
- Always sort rules deterministically.
- Use stable output ordering.
- Golden tests must verify stable outputs.

## 17. Next-question engine

The next-question engine supports progressive, low-bandwidth workflows.

Principles:

- Ask danger-sign questions first.
- Ask only one question at a time.
- Prefer yes/no questions.
- Prioritize questions with highest clinical safety importance.
- Respect channel constraints.
- Do not ask long forms first.

Question model:

```yaml
question_id: child_danger_convulsions
module: child_triage
priority: 100
applies_when:
  patient_group: child_0_59_months
text:
  fr: "L'enfant a-t-il eu des convulsions ?"
answer_type: yes_no
maps_to: clinical_inputs.danger_signs.convulsions
clinical_use_status: not_for_real_patient_care
```

Selection algorithm:

```text
1. Determine module from patient context and complaint.
2. Load candidate questions.
3. Remove already answered questions.
4. Sort by priority desc, question_id asc.
5. Return first applicable question.
6. If enough data exists, return can_evaluate_now = true.
```
